# 這個專案在做什麼（給第一次來的人）

> 寫給沒看過這個 repo 的人。假設你會寫程式，但不熟財經、也不熟 LLM pipeline 的設計取捨。
> 已經知道這專案在幹嘛、要找 module 邊界或 runtime 細節的，直接去 [系統概覽](system-overview.md)。

## 1. 這是什麼、為什麼有它

每天台股開盤前，這個系統已經產好一份總經報告：昨晚世界上發生了什麼、可能怎麼影響今天的台股。它在早上五點十分自動跑，沒有人按按鈕。**不過目前沒有線上環境在跑**。以下描述的是這個系統的設計與它運轉時的樣子，在本機仍然跑得起來。

起點是一個問題：AI 能不能穩定做出「開盤前那三十分鐘的財經直播」那種東西——講當天的總經與盤勢，每天早上準時出現。我想複製的不是任何人的講解風格，是「每天都在」這件事：一個人很難每天早上準時把昨晚整個世界的財經新聞消化完，但一條管線可以。

分界線在這裡：這類節目多半只談總體，不碰個別產業與個股。這個系統刻意往下走一層。它的核心輸出不是一段摘要，而是一串**連動鏈**，每一條都長成「哪個產業、透過什麼機制、牽動哪些標的、往哪個方向」。

以 repo 內的合成範例為例（[canary-example](../../apps/server/tools/eval/fixtures/canary-example/2026-03-02/brief.json)，虛構的公司、數字與新聞）：那天的報告判定當天有四股力在拉扯（半導體與資料中心供應鏈、貨櫃航運、商用不動產與金融放款、內需服務業），底下掛了 3 條連動鏈。

所以這不是新聞摘要工具。摘要回答「發生了什麼」，這個系統要回答「所以會影響什麼、為什麼」。名字就是這個意思：Suanomics，中文叫「掐指連總經」——「掐指」是算，「連」是連動。

它服務的是想用總經視角看台股、但沒時間每天追國際新聞的人。它不是投資工具，也不會告訴你該買什麼——法規上不能，設計上也刻意不做（第 7 節會講清楚界線在哪）。

### 現在做到哪、還差在哪

一開始就拿真人節目當對照，好處是差距很具體。2026 年 6 月底做過一次逐項比對，診斷出三個差距：報告裡沒有鮮活的具名數字、沒有一條貫穿全文的主軸、缺少觀點與前瞻。那三項後來都收斂了，但還沒補的洞講清楚比較有意義。下面照影響大小排：

- **沒有「預期差」**——這是最大的一個。總經報告最有解釋力的其實不是「數字是多少」，而是「這個數字比市場預期高還是低、公布之後哪個資產先動」。目前只有實際值，沒有市場預期值可以對照，所以報告講得出「CPI 是多少」，講不出「這比大家想的高」。
- **來源不分官方與轉述**。央行公告和媒體二手轉述目前吃同一組權重（0.9–1.1 的溫和乘數），還沒有分級。
- **抽出來的證據偏向支持側**。報告會給出主軸，也會給出挑戰主軸的反面觀點，但挑戰用的那些數字（外資賣了多少、指數跌了多少、有多少資金押在下跌那一邊）常常沒被抽進可追溯的證據池——於是講正面時查得到依據，講反面時查不到。已經量到、修法在跑，還沒收斂。

如果你是來看程式的：這個 repo 比較值得看的不是「串了 LLM API」那部分，而是它有一整套量尺在回答「這次改動讓報告變好還是變壞」。那在第 6 節。

## 2. 讀下去需要的四個詞

這四個詞後面每一節都會用到。其餘術語會在各自登場的地方就地解釋，完整清單在最後的附錄。

**brief（每日報告）** — 系統每天產出的那份東西，實體是一份 JSON，也是網站上你看到的那一頁。它不是一段文字，是一個結構：主標、當日主軸、敘事段落（最多四段）、連動鏈、正反觀點、引用來源、關鍵數字、行事曆事件。以 repo 內的合成範例為例，那天的主標是「出口動能延伸與物價黏性並現，政策路徑成市場焦點」，敘事寫了三段：出口動能延伸，資料中心資本支出未見降溫；物價黏性升溫，政策路徑判斷更趨複雜；航運報價彈升與金融放款品質的邊際訊號。

**連動鏈（cascade chain）** — 一條「A 發生了，所以 B 會怎樣」的推論，固定四個欄位：產業、機制、受影響標的、方向。以前面同一個合成範例為例，那天的其中一條是「半導體與資料中心供應鏈／海外資料中心維持高強度資本支出，帶動先進封裝與高速運算晶片訂單能見度延伸，供應鏈上游廠商產能利用率同步上升／示例科技供應鏈／正向」。一天會產出幾十條。連動是產品名字的來源，也是它跟新聞摘要的分界線。

**敘事線（storyline）** — 跨日的線。單日報告講今天，敘事線記的是「這個判斷從哪天開始、後來怎麼了」。資料庫裡它有四種狀態：open（還在跑）、confirmed（後續發展支持了）、refuted（被推翻）、dormant（沒動靜了）。這是系統唯一會把昨天的判斷帶進今天的通道。

**agent** — 這個詞在這裡不是你熟悉的那個意思。它不是會自己規劃、自己挑工具、跑迴圈跑到滿意為止的自主體。這裡的一個 agent ＝ 一段固定的 prompt ＋ 一個規定輸出長什麼樣的 schema ＋ 一套失敗了怎麼辦的規則。誰在什麼時候被呼叫是程式寫死的；模型唯一能左右流程的地方，是決定要不要展開第二層分析、以及展開誰。為什麼刻意設計成這樣，第 4 節會講。

## 3. 一天是怎麼過的

這一節按時間走，不講 module 名字。規模先給你一個底：21 個新聞來源、26 個外部資料來源（seed 有 30 筆，4 筆已停用）、26 條市場序列、九張資料表、八種背景工作，主分析鏈上六個 agent。

**清晨 05:10（台北，這是設計時假設的觸發時間，實際排程由部署者自備、自行決定）。** 排程一觸發，第一件事不是抓新聞，是問系統「今天該不該產報告」——週六不產（沒有交易日可談），週日產的是本週回顧與下週前瞻，跟平日是不同型態。這個判斷來自一張台美股市的假日表。

**先補資料，再談內容。** 兩件事並行：把 26 條市場序列從 FRED、證交所、期交所、Nasdaq 拉回來；把 21 個新聞來源的 RSS 收一輪，抓內文、分類、打標籤。新聞那一趟實測要 31 分鐘左右；逾時多久算異常、要不要發告警由排程端自己決定，server 不內建這層判斷。

**選稿。** 這裡是第一個 LLM 關卡。候選池是最近兩週的新聞，先用一個純函式評分器排序（看時效、看是否延續既有敘事線、看跨新聞連結、看來源權重），取前 36 則交給 Editor 挑。Editor 挑的不是最新的，是最能組成一天故事的那幾則，順序也是它排的——排前面的會影響後面所有 agent 的鋪陳。這一步失敗（模型壞掉、輸出不合格式）就退回「照時間取最新」，報告一定產得出來。

**逐則拆解。** 每一則被選中的新聞各自跑一條線：先由 Decomposer 拆出主體與可能的連動假設，再用那些假設去資料庫裡撈相關的歷史文章——這一步是 SQL，不是 LLM。撈到的東西連同新聞本文餵給第一層分析，產出連動鏈。如果第一層自己提名了值得再追下去的對象（最多五個），才展開第二層。

**收攏成一天的故事。** 所有新聞的連動鏈匯到 Synthesizer 手上，由它整併出當日主軸與敘事骨架。接著是關鍵的一步：**引用、網址、合規檢查與格式驗證是程式做的，不是模型做的**。模型只能從一份白名單裡挑來源，網址由程式組，投信投顧法的禁用字眼由程式攔。

**寫成給人讀的文章。** Narrative Writer 拿骨架寫成敘事段落（schema 限制最多四段），這是網站上讀者真正看的東西。另有一個 agent 專門產「支持這個主軸／挑戰這個主軸」的正反觀點區塊。

**接著是聲音。** 報告存檔之後，另一個工作把它改寫成 podcast 逐字稿——不是把報告念一遍，是另一種文體（有人設、有口語節奏）。再另一個工作把逐字稿送去語音合成，音檔存到 Cloudflare R2。這兩步都是盡力而為：失敗不會讓報告消失。

**早上你打開網頁。** 前端跟 API 要當天的報告，拿到那份 JSON，渲染成你看到的頁面。這時候不會有任何 LLM 被呼叫——報告在天亮前就寫好了，網頁只是把它讀出來。

值得注意的是有幾步**刻意不用 LLM**：撈相關文章是 SQL，引用組裝是程式，首頁那張「本日關鍵數字」卡片是純資料直出。用得起模型的地方不代表該用模型——凡是有明確對錯的事（網址對不對、有沒有踩到禁用詞、數字要不要轉單位），交給程式比交給模型可靠，而且免費。

## 4. 為什麼是一群 agent，不是一次 prompt

先講一件事：這個 repo 一開始真的是一次 prompt。那份程式現在還在（`apps/server/src/brief/prompts.ts`，43 行，最後一次被碰是 2026 年 5 月），但已經沒有任何呼叫端。它被換掉不是因為「multi-agent 比較潮」，是因為單一 prompt 在下面五件事上做不到。

**失敗的顆粒度。** 一次 prompt 只有兩種結果：成功、失敗。拆開之後，每一步失敗時的處置可以各自不同——選稿失敗就退回照時間取最新（報告照出）；某一則新聞分析失敗就丟掉那一則（存活少於兩則才整份失敗）；合規檢查沒過就要求重寫，最多三輪；最後的寫作失敗則是報告照樣落地、只是少了那段長文。這些差異不是實作細節，是「每天都要有報告」這個承諾的實作。

**中途要去查資料庫。** 拆解新聞得到的假設，要拿去資料庫裡撈相關的歷史文章，撈完再餵給下一步。一次 prompt 做不到這件事——除非給模型工具讓它自己查，但那就變成一個沒人知道會跑幾輪、花多少錢的迴圈。切開之後，那一步就是一句 SQL。

**每一步的輸出可以被檢查。** 連動鏈固定四個欄位，格式不對當場擋掉、重問。一整篇文章的內部結構沒辦法這樣驗——你不能對一段散文說「你第三段的產業欄位缺了」。

**引用的白名單才守得住。** 每一步只准引用「餵進這一步的那些來源」。範圍小，所以驗得動：模型編出一個不存在的網址，程式當場比對得出來，重問最多三次，還是不行就把那條引用拔掉、保留分析。混成一次 prompt 的話，所有來源攤在一起，這道檢查就形同虛設。

**改壞了知道是誰壞的。** 第 6 節那套量尺是逐個 agent 做 A/B 的。全部混成一段 prompt，你只能量最終輸出——改完變差了，不知道是選稿變差、分析變差，還是文筆變差。

### 六個 agent 各自在幹嘛

順序就是它們被呼叫的順序。

**Editor（主編）** — 從排序過的候選裡挑 5 到 8 則，定出當天的 1 到 2 個主軸，順便判斷既有敘事線是被支持、被挑戰、還是有新進展。它挑的不是最新的，是最能組成一天故事的。它有一個特別設計：輸出拆成兩份獨立契約，選稿一份、敘事線一份，各自驗證——選稿壞掉時敘事線照樣寫回資料庫，不會因為一次幻覺的新聞 id 就把當天的長期狀態一起賠掉。

**Decomposer（拆解）** — 每一則新聞各跑一次。把新聞拆成主體、主題標籤，和最多六條「可能會連動到哪裡」的假設。每條假設自帶一句檢索查詢，那句話等一下會變成資料庫查詢。它的 prompt 有一條規定：講產業或公司的新聞，至少要提一條跨到地緣、政策或監管的假設——這是刻意逼它跳出同溫層。

**Tier 1 Analyst（第一層分析）** — 拿新聞本文、拆解結果、以及撈回來的相關文章，寫出第一層連動鏈：哪個產業、什麼機制、哪些標的、什麼方向、引用哪幾則。它還可以提名最多五個「值得再往下追一層」的對象。

**Tier 2 Analyst（第二層分析）** — 只有第一層真的提名了對象才會跑。它沿著單一條第一層的鏈往下推第二層傳導。有兩個刻意的限制：它不能把第一層的結論當引用（只能當背景），而且它**沒有能力提名第三層**——那個欄位在它的輸出格式裡根本不存在，所以推論深度天生就是兩層，不是靠 prompt 拜託它停。如果它寫出來的鏈一條引用都沒有，程式會替它標上「推測」，讀者面必須用條件語氣呈現。

第一層與後面的寫作步驟沒有這個標記，走的是另一條規則：引用只能從白名單裡挑，編出白名單外的網址會被要求重寫，重寫幾次還是不行就把那條引用拔掉、保留分析本身。真的完全找不到佐證時，系統寧可明講「資料不足」，也不補一個看起來像來源的東西上去。

**Synthesizer（整併）** — 到這裡從發散轉收斂。它把所有新聞的連動鏈收進來，找出跨新聞的共同傳導，產出主標、摘要、當日受影響的產業與 ETF、推理鏈。它只產文字和新聞 id，**不產網址**——真實網址、引用清單、免責聲明全部由程式在下一步組裝。

**Narrative Writer（寫作）** — 拿組裝好的報告寫成給人讀的長文，最多四段，段落之間跨新聞編織而不是逐則摘要。這是網站上讀者真正在讀的東西，也是整條鏈上**唯一用比較貴的模型**的一步（其餘五個都跑同一個便宜的快模型）。這份文件刻意不寫死是哪個型號——每個 agent 用哪個模型可以用環境變數逐個覆寫，實際型號寫在 [Agents 與 Prompts](agents-and-prompts.md)，而且會隨市場上的選擇換。它失敗兩次就放棄，回傳 null——報告照樣上線，只是那天沒有長文。

### 主鏈之外

還有幾個不在這條鏈上、但每天都會跑的：一個專門產「支持這個主軸／挑戰這個主軸」的正反觀點區塊；一個把報告改寫成 podcast 逐字稿（不同文體，有人設）；新聞進來時還有分類與打標籤兩支。另外有三個「評審」只在你手動跑評測時才會出現，它們屬於第 6 節。

## 5. 資料住哪

一個 Postgres、九張表。先給你全景，後面再逐組講：

| 組別 | 表 | 裝什麼 |
|---|---|---|
| 素材 | `news_sources` / `news_items` | 21 個 RSS 來源與收進來的新聞＝候選稿源 |
| 素材 | `external_sources` / `external_articles` | 來源清單的背景文章庫（seed 30 筆、其中 4 筆停用），分析時拿來佐證 |
| 素材 | `market_data_points` | 26 條市場序列的數值 |
| 產出 | `daily_briefs` | 每日報告，一天一列 |
| 產出 | `analyses` | 使用者自己貼新聞做的即席分析（快取性質） |
| 跨日狀態 | `storylines` | 敘事線，唯一把昨天帶到今天的表 |
| 執行紀錄 | `background_jobs` | 每次背景工作的稽核紀錄與成本明細 |

### 兩個新聞池，用途不一樣

這是最容易搞混的地方。系統有**兩套**新聞資料，不是備份關係。

`news_sources` / `news_items` 是**候選稿源**：21 個 RSS 來源，每天收一輪，回答的是「今天要報哪幾則」。Editor 從這裡挑。

`external_sources` / `external_articles` 是**背景資料庫**：seed 有 30 筆來源、其中 4 筆已停用，實際會抓的是 26 個。停用的原因有兩種：feed 本身沒了，或站方不允許自動化存取（2026-08-22）。回答的是「要佐證某個推論時，過去有什麼相關報導」。它比前者重——每篇文章都經過一次 LLM 加工，產出中性摘要、抽出的實體、主題標籤，而且**連這篇花了多少錢、用哪個模型都記在列上**（`llm_model`、`llm_cost_usd`）。分析階段撈的是這個池子。

兩者都靠唯一約束擋重複：新聞是「來源 + 對方的 id」，外部文章是「來源 + 網址雜湊」。同一則東西抓兩次不會變成兩列。

### 分類是兩層的，而且永遠有退路

新聞分類這件事有一個容易踩的坑：交給 LLM 打標，那 LLM 沒打到的時候怎麼辦？這裡的解法是兩層。

**來源層**是靜態的：每個 RSS 來源在建檔時就標好是 `tw-equity`（台股）還是 `macro`（總經），而且型別上強制——加新來源不標就編譯不過。

**項目層**是動態的：新聞收進來時由一個 LLM 打五選一的細標籤（科技半導體／台股其他／總經／能源／國際），存進 `news_items.category`。

如果項目層是空的或值不合法，程式會**從來源層推一個粗桶**回來。所以分類永遠有值，選稿不會因為某天 LLM 沒標到就整個歪掉。這個退路的存在，是為了讓「維持類別廣度」那條選稿規則不會突然失效。

另外還有一組多選的 `topic_tags`（也是 LLM 打的），用途不是分類而是**聚類**——判斷「這五則其實在講同一件事」，避免同一個事件灌爆當天的候選池。

### 市場數字：刻意極簡

`market_data_points` 只有三個有意義的欄位：序列 id、日期、數值。26 條序列全部長這樣，唯一約束是「同一序列同一天只有一列」。

刻意的是：所有換算（年增率、利差、單位轉換）在**寫進資料庫之前**就做完。資料庫裡躺的永遠是可以直接顯示的數字，不是原始值加一堆待處理的邏輯。

### 產出

`daily_briefs` 一天一列，`brief_date` 有唯一約束。只有少數欄位是真欄位（日期、選了哪幾則新聞的 id、摘要），**整份報告是一個 jsonb**。原則是「要拿來查的才開欄位，其餘整包丟 jsonb」。

`analyses` 存的是即席分析：網站上有一個頁面可以自己貼一則新聞進去、要系統當場分析，結果就存在這裡。它有 `expires_at`——這張表本質上是快取，不是檔案庫。

### 跨日狀態

`storylines` 是唯一會把昨天帶到今天的表。每條線有標題、論點、狀態（open／confirmed／refuted／dormant）、涉及的實體，以及一串 update 紀錄。第 2 節提過它。

### 執行紀錄

`background_jobs` 記每一次背景工作：哪一種、狀態、試了幾次、跑到哪（進度）、結果指向哪裡、錯誤訊息。八種工作類型與四種狀態都用資料庫層的 check 約束釘住。**它是唯一的一份**——2026-09-04 之前佇列自己還存著另一份狀態，兩份對不上的時候沒有人是對的。

這張表有個地方值得知道：`metadata` 這個 jsonb 欄位裡，**每天的報告工作都會把當次每一通 LLM 呼叫的明細整包寫進去**——哪個 agent、進出多少 token、花多少錢、重試幾次、有沒有踩到合規攔截。線上要觀察「模型最近是不是常失敗、成本有沒有失控」，就是拿 SQL 查這個欄位——那些數字在程式碼裡沒有讀取端，讀它的是人。

### 不在資料庫裡的東西

podcast 音檔存在 Cloudflare R2，資料庫只留一個路徑。**等待中與執行中的工作只活在 server process 的記憶體裡**——它重啟一次，排隊中的工作就沒了（開機時會把那些 row 標成失敗，靠下一次觸發補）。`background_jobs` 不是那份佇列的副本，它就是可查詢的那一份真相：狀態、重試次數、進度全在同一筆 row。prompt 不在資料庫裡——它們是程式碼，跟著 git 走版本。

最後一個刻意的缺席：**沒有向量檢索**。撈相關文章用的是實體與標籤的 SQL 查詢，不是 embedding。理由寫在專案規則裡——目前這個資料量硬塞進 prompt 就夠用，加一層向量索引買不到對應的東西。

## 6. prompt 從哪來、怎麼知道改好了還是改壞了

這一節是這個 repo 跟多數「串了 LLM API」的專案差最多的地方。

### prompt 是程式碼

線上跑的 prompt 就是 TypeScript 檔案（`agents/<名字>.prompt.ts`），跟著 git 走版本，改它要開 PR。沒有資料庫裡的 prompt、沒有後台編輯器。

### 但它們不是憑空寫的

有一條蒸餾管線，把外部素材變成 prompt 候選：

**素材進來** — YouTube 頻道的逐字稿（第 1 節提到的那個參照對象就是其中一個來源）、podcast RSS、外部的分析方法論文件。音訊會先轉成逐字稿。

**六個角度平行抽取** — 同一份逐字稿被六個不同的 lens 各讀一遍：抽事件與日期、抽它引用了哪些來源、抽提到的實體、抽推理鏈、抽它判斷的產業影響、抽可重用的分析框架。（這六個跟第 4 節那六個 agent 沒有關係，是另一組東西，只是剛好都是六。）切成六個而不是一次問完，理由跟第 4 節一樣：每個角度的輸出格式不同，分開才驗得動。

**整併與蒸餾** — 多集的抽取結果整併成一份長文，再蒸餾成結構化的 digest。

**編譯成候選** — digest 編譯成 candidate prompt 檔，落在 gitignore 的目錄裡。

**然後停下來，等人。** candidate 是**全量**的——所有抽出來的框架、詞彙、紅旗全部塞進去。要哪幾條、怎麼措辭、要不要拆成兩個 tier，由人在貼進 production prompt 時決定。這個關卡是刻意留的：2026 年 6 月曾經有過一層自動化的取捨機制，後來拿掉了，把判斷還給人。

**誠實話**：這條管線機制是健全的，但實際評估過「把它接進日常流程」的結論是 NO-GO——不是管線不能跑，是抽出來的素材太薄，值不回接線的複雜度。真正被 promote 進 production 的，是一個手工挑出來的分析框架。**機制健全不等於素材有價值**，這兩件事得分開判斷。

### 怎麼知道改好了還是改壞了

這是整件事最難的部分。改一行 prompt 之後，你沒有任何測試可以斷言「今天這篇比昨天好」。所以要有量尺。

**機械的那半**可以自動判：報告裡每個數字能不能追回它的來源？有沒有出現投信投顧法禁用的字眼？版面在各斷點有沒有壞？這些有明確對錯，寫成測試與稽核腳本就好。

**主觀的那半**沒有對錯，只有比較。做法是找一個 LLM 當評審，但**不給分數，只做兩兩比較**——「這兩版哪一版比較有深度」而不是「這版深度幾分」。理由是絕對評分在深度這種維度上會飽和，兩版都給 4 分，你得不到訊號。

比較用的輸入是固定的：留了幾天真實的歷史資料當標準題目，改動前後各跑一次，同一份輸入、只差你改的那個東西。

**換模型走另一條路。** 有專門的 A/B 工具，而且它強制先做一件事：**同一個模型跑兩次，看它自己跟自己差多少**。沒有這個雜訊底線，你會把模型的隨機波動讀成「新模型比較好」。2026 年 8 月初有一次就是這樣——補了對照組之後，結論方向是反的。

每一次量測都要在趨勢日誌上留一列。那份日誌就是 repo 裡的一個內部品質趨勢文件，量測工具跑完會自己 append 一列，人再回頭補上判讀。工具建了但沒人記錄，等於沒有——這條是踩過才加的紀律。

### 這裡學到最貴的一課

量測工具的失敗模式不是「跑不動」。跑不動你會發現。真正的失敗模式是**跑完了、數字看起來合理、但量到的是錯的東西**。這個 repo 踩過的真實案例：

- 把支持某個結論的證據算成反向的證據——分子分母都對，方向錯了。
- 單位盲：`30%` 跟 `30萬` 被判成同一個數字。
- 量測過程中把能推翻自己結論的素材丟掉了。
- 量測還在跑，同時有人改到被量測的那段程式。
- 用錯量尺：上面說的「固定幾天標準題目」那套（repo 裡叫 canary）是拿**既有的報告**做對照實驗、不重跑管線，所以**改 prompt 它完全量不到**——跑起來一片綠，但什麼都沒驗到。那次改用另一支會真的重跑一次的工具，才看見差異。

這些每一條都是實際發生過的，而且幾乎都是由一個沒有前情脈絡的檢查者抓出來的——寫的人自己看不到，因為他知道答案。這件事後來變成了這個專案的一條紀律：**驗收不由製作者自己做**。

## 7. 這個專案不做什麼

### 法規那條線

台灣的投信投顧法規範誰可以提供投資建議。這個系統**不是**投顧、也不打算是，所以它在設計上就不能對個股或 ETF 給出買、賣、持有、加碼、減碼的指示，也不能用保證獲利或斷言漲跌的語氣。它只提供描述性的脈絡與條件式的傳導分析，每份報告都帶免責聲明。

這條線不是靠 prompt 拜託模型遵守，是程式在輸出前掃過一遍：一份禁用語清單，加上一道「個股名稱附近有沒有出現方向性用語」的鄰近檢查。掃到就要求重寫，重寫幾輪還是不行就把違規的句子拿掉。

**誠實說**：這是文字比對層級的攔截，不等於完整的法律合規保證。它擋得住明講的推薦，擋不住所有暗示。

### 產品範圍外

以下是明確決定不做的，不是還沒做：使用者註冊、登入與付費；LINE Bot；串接券商 API 或管理持股；圖片辨識。這些每一項都會把專案的性質改變——一旦有帳號與持股，「描述性脈絡」就變成「個人化建議」，那是完全不同的法律位置。

### 技術上刻意不做的

沒有向量檢索（第 5 節講過理由）。沒有讓模型自己決定要呼叫什麼工具、跑到滿意為止的自主迴圈（第 4 節講過理由）。

### 它本來就做不好的事

**來源品質決定產出品質。** 系統只能從它被設定的那些來源裡看世界。某個來源當天沒發、或抓取失敗，那個角度當天就是空的。

**第二層推論可能沒有證據。** 如果第二層分析寫出來的鏈一條引用都沒有，程式會把它標成「推測」並要求用條件語氣呈現。標記是程式判的，不是模型自報的——但它終究是一條沒有佐證的推論。

**它不預測。** 報告講的是「已經發生的事可能怎麼傳導」，不是「明天會漲會跌」。這既是法規要求，也是這套方法本身的邊界。

## 附錄：完整詞彙表

第 2 節那四個詞不重複，這裡收其餘會遇到的。

**產出相關**

| 詞 | 意思 |
|---|---|
| 當日主軸（thesis） | 一天只有一句的核心判斷，由 Editor 產出，貫穿整篇敘事 |
| 敘事（narrative） | 讀者面的長文，最多四段，跨新聞編織而不是逐則摘要 |
| 正反觀點（viewpoints） | 顯性的「支持這個主軸／挑戰這個主軸」區塊，獨立於敘事 |
| 推理鏈（reasoning chain） | 報告裡列出的推論步驟，2 到 6 條 |
| 推測（speculative） | 第二層連動鏈沒有任何引用時，由程式蓋的標記 |

**管線相關**

| 詞 | 意思 |
|---|---|
| 第一層／第二層（tier 1／tier 2） | 連動推論的兩層深度。第二層只在第一層提名對象時才跑，而且結構上無法再產生第三層 |
| 選稿（selection） | 從候選池挑出當天要報的 5–8 則新聞，以及它們的順序 |
| 降級（degrade） | 某一步失敗時的退路，例如選稿失敗退回照時間取最新 |
| 合規閘（compliance gate） | 輸出前掃禁用語與個股方向性用語的程式檢查 |
| 白名單（allowlist） | 每個分析步驟只准引用「餵進這一步」的那些網址 |

**證據相關**

| 詞 | 意思 |
|---|---|
| claim | 從分析中抽出的單一主張，帶類型（具名數字／已發生事件／因果推論）與證據指向 |
| 證據帳（ledger） | 一份報告裡所有 claim 的集合，供追溯與稽核 |
| 追溯率（traceability） | 讀者看到的數字裡，有多少比例能對回證據帳 |
| 新鮮度（freshness） | 每條市場序列「最新一筆該是哪天」的預期，用來判斷資料是不是過期了 |

**量測相關**

| 詞 | 意思 |
|---|---|
| canary | 固定幾天的真實歷史輸入，當作改動前後的標準題目 |
| 對照實驗（ablation） | 把報告的某個成分拿掉，跟完整版對打，看那個成分有沒有貢獻 |
| judge | 當評審的 LLM。只在手動跑評測時出現，不在每日生產鏈上 |
| pairwise | 兩兩比較而不是打分數的評審方式 |
| 雜訊底線（noise baseline） | 同一個模型跑兩次的差異。沒有它就分不出「新模型比較好」和「隨機波動」 |
| smoke | 拿手工構造的輸入真的打一次 LLM，看產出有沒有走鐘 |

**蒸餾相關**

| 詞 | 意思 |
|---|---|
| lens | 從逐字稿抽取的六個角度之一（事件／引用來源／實體／推理鏈／影響／分析框架） |
| digest | 蒸餾後的結構化中間產物，供編譯成 prompt 候選 |
| candidate | 編譯出來的 prompt 候選，**尚未上線**，要人工挑選後才貼進 production |
| promote | 把候選內容人工挑選、改寫後放進線上 prompt 的動作 |

**文件與註解的用語**

| 詞 | 意思 |
|---|---|
| prod（技術意義） | `NODE_ENV=production` 下的行為，或每日 pipeline 的正式路徑——相對於 eval、canary、smoke 這些量測用的路徑。例：「prod 行為」「prod 的 orchestrator」「prod brief」 |
| prod（帶日期的量測） | 「prod 實測」「2026-08-10 的 prod brief」這類帶日期的數字與案例，出自作者自己跑過的環境，是歷史量測，不是一個現在對外提供的服務——這個專案目前沒有線上 demo、也沒有代管服務。拿這份 codebase 在乾淨環境重跑，不保證量到同樣的數字（來源清單與累積的資料都不同） |
